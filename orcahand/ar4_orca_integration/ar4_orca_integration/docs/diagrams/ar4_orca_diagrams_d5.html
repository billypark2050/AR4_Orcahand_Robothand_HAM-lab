D1 · 아키텍처

어떤 코드가 어느 층에 있고 누가 누구를 쓰는가. 위는 launch 시점에 조립되는 로봇 모델(description 계보), 아래는 실행 중 레이어입니다. 같은 층에서 왼쪽이 팔, 오른쪽이 손이며 맨 아래에서 손이 커넥터(hand_connector)로 팔 J6에 고정됩니다.

  • description 계보: 공식 orcahand_description → orca_ui 번들 → orcahand_ros_description → ar4_orca_description. 실행 중에는 공식 저장소를 쓰지 않습니다(반투명).
  • 코드 위치: 파랑 = ar4_ros_driver/, 초록 = orcahand/orca_core·orca_ui·orcahand_description, 주황 = orcahand/ar4_orca_integration/. ROS 배지는 apt로 설치된 ROS 2 패키지(ros2_control, MoveIt, rviz2 등)이고, 색은 그것을 쓰는 쪽(팔이면 파랑)입니다.
  • 점선 블록 ar4_orca_moveit_config는 아직 없습니다(Phase 2). orca_ui는 ROS를 끈 상태에서 캘리브레이션·텐셔닝용으로만 씁니다.

D2 · 시작 순서

ros2 launch ar4_orca_bringup bringup.launch.py 한 줄 이후 무엇이 어떤 순서로 켜지는가. 오른쪽 열은 해당 코드 위치입니다.

  • 4~23은 거의 동시에 시작합니다. launch 파일이 순서를 보장하는 곳은 JSB가 끝난 뒤 JTC를 켜는 14→15뿐입니다.
  • 19에서 캘리브레이션이 안 된 config이면 핸드 드라이버는 시작을 거부하고 종료합니다. 자동 캘리브레이션은 하지 않습니다.

D3 · 통신 아키텍처

실행 중 노드들이 어떤 이름과 방식(topic, service, action)으로 연결되는가, 그리고 USB 아래에서 쓰이는 장치 프로토콜.

  • /joint_states 하나에 두 발행자가 있습니다: 팔(joint_1..6, 60 Hz)과 손(hand_* 17개, 50 Hz). robot_state_publisher가 둘을 합칩니다.
  • ARHardwareInterface와 TeensyDriver는 별도 노드가 아니라 controller_manager 프로세스 안에서 플러그인으로 돕니다.
  • /joint_trajectory_controller/controller_state, /orcahand_driver/commanded_joint_states 같은 모니터링 토픽은 그림에서 생략했습니다.

D4 · 실행 추적 (Command ↓ / Feedback ↑)

명령 하나가 모터까지 내려가는 길과 측정값이 RViz까지 올라오는 길. 팔과 손이 나란히 있고, 가운데 세 블록을 함께 씁니다.

  • 팔: position+velocity 명령 설정이라 JTC가 PID 보정 없이 궤적 속도를 그대로 내려보내고(MV…), 엔코더 값은 표시와 허용오차 초과 시 중단에 쓰입니다.
  • 손: 위치를 실제로 맞추는 폐루프는 각 Dynamixel 안(PID loop)에 있고, 올라오는 손가락 각도는 모터 위치로 계산한 추정값입니다.
  • 맨 아래: 손은 커넥터(hand_connector)로 팔 J6(ee_link)에 고정되어 팔이 움직이면 손 전체가 함께 움직입니다. 장착 위치는 mount.yaml에 있습니다.

D5 · 내부 코드 구조 (orcahand_driver ↔ orca_core)

손 쪽 드라이버가 orca_core의 어떤 파일·클래스를 어떤 순서로 부르는지. 위 그림은 파일과 클래스의 관계, 아래 그림은 실행 순서입니다. 2026-10-24 코드 기준.

D5-b · 실행 순서 (함수 호출)

  • 두 층 구조: hand_driver_node.py는 ROS 인터페이스만, hand_backend.py는 ROS 없이 orca_core를 감싸는 로직(단위 변환·속도 제한·궤적 보간)만 맡습니다. 그래서 backend는 ROS 없이 테스트할 수 있습니다.
  • 명령과 실행이 분리: 토픽·액션·서비스 콜백(⑤)은 _target만 바꾸고, 실제 모터 쓰기는 50 Hz _tick(④) 한 곳에서만 일어납니다. 그래서 어떤 입력이 와도 최대 180°/s 제한이 항상 걸립니다.
  • 클래스 선택: load_hand()는 config에 촉각 센서·관절 엔코더가 있는지와 mock으로 8개 클래스 중 하나를 고릅니다. 지금 설정에서는 OrcaHand(실기) / MockOrcaHand(mock)이고, 둘은 모터 클라이언트만 다릅니다.
  • 캘리브레이션: 결과는 config.yaml 옆 calibration.yaml에 저장되고 생성 시(①) 읽힙니다. init_joints()는 미캘리브레이션이면 스스로 캘리브레이션을 돌리지만, 드라이버는 그 전에 ensure_calibrated()로 막습니다(ROS 실행 중 손이 갑자기 움직이지 않도록).
  • 각도 계산: 손가락 각도는 관절 엔코더가 아니라 모터 위치를 캘리브레이션 값(하한·비율·±2π 보정)으로 환산한 추정값입니다.
